## 2. 면접 질문 → 답

**Q. ECS 가 왜 빠른가요?**
같은 컴포넌트 조합(아키타입)의 엔티티를 청크에 **빈틈없이** 모아 두고, 시스템은 필요한 컴포넌트 배열만 처음부터 끝까지 훑는다. 메모리 접근이 연속이라 캐시에 잘 맞고, 청크 단위로 워커에 나눠 주기 쉽다. 거기에 Burst 가 SIMD 를 쓰는 네이티브 코드로 바꾼다.
- 실측(2단계): 큐브 엔티티 하나 약 250바이트, **청크당 64개**, 1만 개 = 157청크. 프리팹 엔티티는 `Prefab` 태그 때문에 아키타입이 달라 **혼자 청크 하나**를 쓴다.

**Q. Job 으로 바꾸면 빨라지나요?**
"얼마나, 누가 기다리는가" 를 재 봐야 안다 (4단계, 적 5만 개 추격).

| 방식 | ms | 배율 |
|---|---|---|
| 메인 스레드, Burst 없음 | 4.36 | 기준 |
| 메인 스레드, Burst | 0.28 | **15.6배** |
| Job `.Schedule()` (워커 1개) | 0.29 | Burst 와 같음 |
| Job `.ScheduleParallel()` | 0.114 | 추가로 **2.5배** |

- 코어가 15개여도 2.5배였다. 워커들이 동시에 시작하지 않았고, 같은 시간대에 렌더링 Job 이 워커를 같이 썼다.
- 바로 뒤의 `RotationSystem` 이 같은 `LocalTransform` 에 메인 스레드에서 쓰려고 `ChaseJob` 을 **기다렸다.** ECS 는 엔티티가 아니라 **컴포넌트 타입 단위**로 충돌을 추적한다. 프로젝트가 플레이어 위치를 `PlayerPosition` 사본으로 따로 두는 이유다.
- 일이 작으면 Job 이 손해다 (청크 2개면 워커를 2개밖에 못 쓰고, 예약 고정 비용이 더 크다).

**Q. 구조적 변경이 뭐고 왜 피하나요?**
`Instantiate`, `DestroyEntity`, `AddComponent`, `RemoveComponent` 처럼 엔티티의 **아키타입이나 청크 배치를 바꾸는** 것. 삭제하면 빈자리를 다른 엔티티가 이사 와서 메운다. 다른 워커가 그 자리를 잡고 있으면 엉뚱한 엔티티를 읽게 되므로, Unity 는 돌고 있는 Job 이 전부 끝난 뒤(sync point) 메인 스레드에서만 허용한다. Job 안에서는 **ECB** 에 적어 두고 나중에 재생한다.

**Q. ECB 를 쓰면 구조적 변경 비용이 사라지나요?**
아니다. **한곳에 모을 뿐**이다 (5단계, 큐브 1만 개가 수명마다 죽고 태어남).

| | 생성·삭제 (ECB) | 풀링 (Enableable) |
|---|---|---|
| 메모하는 시스템 | 0.046 ms | — |
| **ECB 재생** | **0.119 ms** (비용의 약 72%) | 0.0004 ms |
| 메인 스레드 합계 | **약 0.165 ms** | **약 0.010 ms** (약 16배 차이) |
| CPU 총량 | 약 0.165 ms | 약 0.256 ms (워커 조각 합계 포함) |

- 비용은 메모하는 쪽이 아니라 **재생하는 쪽**에 찍힌다.
- 풀링은 일을 줄인 것이 아니라 **메인 스레드에서 워커로 옮긴 것**이다. "풀링이 빠르다" 보다 "메인 스레드가 덜 막힌다" 가 정확하다.

**Q. Enableable 컴포넌트로 풀링할 때 주의할 점은?**
- 우리 `Alive`(프로젝트 `Active`)만 끄면 **렌더러는 모른다.** `MaterialMeshInfo` 도 같이 꺼야 화면에서 사라진다 (직접 겪었다).
- 꺼도 컴포넌트와 데이터는 **붙어 있다.** 쿼리에 `Alive` 조건을 넣지 않은 시스템은 죽은 엔티티도 처리한다 (6단계에서 죽은 표적이 계속 맞았다).
- 꺼진 엔티티도 메모리를 차지하고, 섞인 청크는 체크를 하나씩 보며 건너뛴다. 풀은 "넉넉히" 가 아니라 "필요한 만큼".

**Q. 시스템끼리는 어떻게 통신하나요?**
서로를 부르지 않는다. 앞 시스템이 **싱글턴이나 이벤트 목록에 써 두고** 뒤 시스템이 읽는다. 순서는 `[UpdateBefore/After]` 로 못 박는다 (안 박으면 한 프레임씩 밀리고, 그 순서도 보장되지 않는다).
- 매니지드 입력은 작은 `SystemBase` 하나가 읽어 싱글턴에 쓰고, 나머지는 전부 `ISystem` + Burst 가 그 싱글턴을 읽는다.
- `CreateSingleton` 은 이미 있으면 **만드는 순간 예외**를 던진다 (`OnCreate` 에 둬야 하는 이유).

**Q. 피해를 왜 그 자리에서 깎지 않고 이벤트로 보내나요?**
① 병렬 Job 에서 같은 적을 두 워커가 동시에 때리면 같은 `Health` 에 동시에 쓰는 레이스가 된다. ② 피해를 주는 쪽(투사체·장판·지형)이 늘어도 **적용하는 곳은 하나**로 남는다. 적용 시스템은 "누구에게, 얼마" 만 보고 누가 때렸는지 모른다.
- 처리한 이벤트는 비운다. 비우지 않으면 지난 프레임의 피해가 **매 프레임 다시** 적용된다 (6단계 실험: 1초 머물면 초당 1 이어야 할 피해가 약 30, 떠나도 계속 깎임).

**Q. NativeContainer 는 왜 쓰고, 무엇을 조심하나요?**
Burst·Job 에서는 매니지드 `List`/`Dictionary` 를 못 쓴다. Native 컨테이너는 가비지 컬렉터 밖이라 **만든 쪽이 `Dispose`** 해야 한다 (`OnCreate` ↔ `OnDestroy`, 안 하면 Play 마다 누수가 쌓인다).
- 여러 워커가 동시에 쓰려면 `ParallelWriter`. 대신 **용량을 늘리지 못한다** — 쓰기 전에 확보한다. 가득 차면 에디터는 `HashMap is full` 예외, 빌드는 검사 코드가 빠져 **조용히 틀린다.**
- 시스템이 직접 든 컨테이너는 ECS 가 의존성을 모른다. 채우는 Job 이 끝나기 전에 읽으면 에러다 → `Complete()` 하거나 Job 끼리 핸들을 잇는다.

**Q. 공간 해시는 언제 쓰나요?**
**찾는 쪽이 많을 때.** 7단계(표적 1만 개, 찾는 쪽 = 플레이어 1명):

| | 전부 비교 | 공간 해시 |
|---|---|---|
| 비교 횟수 / 프레임 | 10,000 | **53** (약 190배 감소) |
| 메인 스레드 | **0.046 ms** | 0.112 ms (**2.4배 느림**) |

해시를 만들려면 표적 1만 개를 전부 한 번씩 넣어야 하고, 넣는 일은 거리 비교 한 번보다 무겁다. 찾는 쪽이 1명이면 그 비용만으로 진다. 찾는 쪽이 1만 명(적끼리 겹침 해소)이면 해시는 한 번 만들고 같이 쓴다: 1억 번 → 약 60만 번 (계산). 프로젝트의 `EnemySpatialHash` 가 적 분리·투사체 적중에 쓰이는 이유다.
- 칸 좌표는 `floor` (`(int)` 는 음수에서 0 쪽으로 잘려 0번 칸만 두 배가 된다). 칸 크기는 찾는 반경·물체 간격 정도. 서로 다른 칸이 같은 키가 되면 여러 칸 조회에서 **중복 처리** → 칸 소속을 다시 확인한다 (ISSUE-011).

| 단계 | 처음 | 실제로 일어난 일 | 배운 것 |

## 4. 자주 막힌 지점과 통한 설명

- **struct 복사**: `GetComponent` 결과·`RefRW` 변수·`.ValueRO` 사이에서 5단계까지 세 번 막혔고, 6단계에서 "`GetSingleton` 으로 받은 건 값이라 바꿔도 싱글턴은 그대로" 를 바로 맞혔다.
- **ECB 의 시점**: "삭제한 다음 줄에서 어떻게 그 엔티티를 읽나" — 위치 (3, 5) 큐브 하나를 **줄 단위로 따라가는 표**에서 풀렸다. 루프 중에는 아무것도 바뀌지 않고, 재생 때 메모된 **값**이 쓰인다.
- **"엔티티가 행동한다" 는 생각**: "타겟이 이벤트를 발생시킨다" 고 했다가 고쳤다. 엔티티는 데이터, 행동은 시스템.
- 추상적인 말(주소, 비트)보다 **값 하나를 따라가는 표와 그림**이 잘 통했다.

## 5. 프로젝트 코드와 같았던 것 / 한 단계 더 나간 것

| 내가 짠 구조 | 프로젝트와 같음 | 프로젝트가 더 한 것 |
|---|---|---|

| 공간 해시 | `floor`, 용량 확보(`WithoutFiltering`) | 위치를 해시에 복사(`AgentRef`), `IsInCell`, `Complete` 대신 Job 핸들 연결 |

## 6. 수치를 말할 때 붙일 조건

- 전부 **에디터 Play 모드**, 안전 검사 켜짐. 빌드에서는 달라진다 → 배율로 말한다.
- 4단계 수치는 CPU·Jobs 설정을 기록하지 못한 측정이다 (워커 15개로 논리 16코어를 추정, 나중에 같은 PC 로 확인).
- 5·7단계는 Profiler 캡처를 저장해 마지막 60프레임 **중앙값**을 프로그램으로 읽었다.
- 계산값(예: 1억 → 60만)은 측정이 아니다.
